# Requirement Analysis

## 1. Business Problem

The project addresses the lack of a unified platform for managing film photography contests. Existing contest operations typically depend on disconnected tools such as online forms, spreadsheets, email, cloud drives, and social media. This creates fragmented data, weak traceability, difficult verification, inconsistent judging, and poor long-term archival value.

The target system must support the full business lifecycle of a film photography contest while preserving analog-specific technical metadata such as film stock, roll, frame, camera, lens, scan details, and provenance.

## 5. Role & Permission Baseline

### 5.1 Role Model

- A single user account may hold multiple roles.
- Role membership is explicit and managed separately from user identity.
- `Participant` has a dedicated profile because participant-specific metadata is required.
- `Organizer`, `Judge`, and `Administrator` are role memberships on the user account; additional profile tables are not required at this stage.

### 5.2 Baseline Permissions

| Role | Core Permissions |
| --- | --- |
| Administrator | Manage user accounts, activate/deactivate users, assign roles, manage reference data, view audit logs, monitor platform health, override or unlock operational issues when policy allows |
| Organizer | Create and update contests, categories, rounds, criteria, award definitions, review registrations, verify submissions, review AI flags, assign judges, finalize results, publish outcomes, archive winning works |
| Judge | Read assigned submissions and criteria, create and submit evaluations, revise draft evaluations before deadline, view only scoped judging workload |
| Participant | Maintain participant profile, register for contests, create film rolls and frames, submit entries, monitor submission and registration status, view published results and personal evaluation feedback where allowed |

### 5.3 Access Model Notes

- `Official Requirement`: The platform must enforce role-based access control.
- `Proposed Business Rule BR-P-001`: A user may hold multiple roles simultaneously, but operational actions must still be authorized per role context.
- Enforcement: Application-design layer and authorization model, not only the database.

## 6. AS-IS Process

### 6.1 Summary

Current contest operations use disconnected tools:

- Announcement via social media or email
- Registration via online form
- Submission via drive links or email
- Verification via manual spreadsheet review
- Judge assignment via ad-hoc communication
- Scoring via separate files or sheets
- Results compiled manually
- Archive kept inconsistently or not at all

### 6.2 AS-IS Problems

1. Data is fragmented across tools.
2. Submission provenance is hard to verify.
3. Deadline and eligibility decisions are manually error-prone.
4. Judges lack a controlled work queue and consistent criteria.
5. Final ranking and award publication require manual consolidation.
6. Historical reuse of winning entries is unreliable.

## 7. TO-BE Process

### 7.1 Summary

The future-state system centralizes contest planning, participant registration, film asset management, submission, verification, judging, result finalization, and archival reuse in a single governed platform.

### 7.2 TO-BE Benefits

1. Unified source of truth for contest and asset data.
2. Structured traceability from participant to roll to frame to submission.
3. Controlled verification and AI-assisted review.
4. Multi-round judging with scoped criteria and judge assignments.
5. Reproducible ranking and result finalization.
6. Searchable long-term digital archive.

## 8. Core Business Flows

Each flow below includes trigger, precondition, main flow, alternatives, outputs, status transitions, data affected, and related business rules.

### F01. Contest Planning and Configuration

- Trigger: Organizer starts a new contest cycle.
- Preconditions:
  - Organizer account is active and has Organizer role.
  - Contest baseline information is available.
- Main Flow:
  1. Organizer creates contest header and schedule.
  2. Organizer defines categories.
  3. Organizer defines judging rounds per category.
  4. Organizer defines scoring criteria and weights for each round.
  5. Organizer defines awards.
  6. Organizer publishes the contest.
- Alternative / Exception Flow:
  - If schedule dates are inconsistent, contest remains draft.
  - If a category has no final judging round, publish is blocked.
- Output:
  - Contest and dependent configuration records.
- Status Transition:
  - `Draft -> Published -> Open -> Closed -> Finalized -> Archived`
- Data Affected:
  - Contest, Category, Judging Round, Scoring Criterion, Award Definition
- Related BR:
  - BR-O-001, BR-O-002, BR-P-007, BR-P-008

### F02. Participant Registration

- Trigger: Participant chooses to join a published contest.
- Preconditions:
  - Participant account is active.
  - Contest registration window is open.
- Main Flow:
  1. Participant submits registration.
  2. System records registration as pending.
  3. Organizer or policy process reviews eligibility.
  4. Registration becomes approved or rejected.
- Alternative / Exception Flow:
  - Duplicate registration attempt is blocked.
  - Registration after deadline is rejected.
- Output:
  - Registration decision and status.
- Status Transition:
  - `Draft -> Pending -> Approved / Rejected / Withdrawn`
- Data Affected:
  - Registration, Audit Log
- Related BR:
  - BR-O-003, BR-P-002, BR-P-003

### F03. Film Roll and Frame Management

- Trigger: Participant wants to prepare contest-ready film metadata.
- Preconditions:
  - Participant profile exists.
- Main Flow:
  1. Participant creates a film roll.
  2. Participant records film stock and processing details.
  3. Participant records frames on the roll.
  4. Participant uploads optional negative/contact sheet references.
- Alternative / Exception Flow:
  - Duplicate frame number within the same roll is blocked.
  - Incomplete frame metadata is saved as draft only.
- Output:
  - Reusable film roll and frame records.
- Status Transition:
  - Film Roll: `Draft -> Ready -> Archived`
  - Film Frame: `Draft -> Ready -> Submitted -> Archived`
- Data Affected:
  - Film Roll, Film Frame
- Related BR:
  - BR-O-004, BR-P-004, BR-P-005

### F04. Film Submission

- Trigger: Participant submits a frame to a contest category.
- Preconditions:
  - Registration is approved.
  - Submission window is open.
  - Frame is in ready state.
- Main Flow:
  1. Participant selects contest, category, and frame.
  2. Participant uploads scanned image and statement.
  3. System validates timing, ownership, and uniqueness.
  4. Submission is saved as pending verification.
- Alternative / Exception Flow:
  - Late submission is rejected.
  - Same frame is already submitted to the same contest.
  - Frame does not belong to the registered participant.
- Output:
  - Submission record awaiting verification.
- Status Transition:
  - `Draft -> PendingVerification -> Verified / Rejected / NeedsClarification -> Judged -> Finalized -> Archived`
- Data Affected:
  - Submission, Audit Log
- Related BR:
  - BR-O-003, BR-O-005, BR-P-006, BR-P-009

### F05. Submission Verification

- Trigger: Organizer reviews a pending submission.
- Preconditions:
  - Submission status is `PendingVerification` or `NeedsClarification`.
- Main Flow:
  1. System evaluates completeness and technical validity.
  2. AI analysis records similarity and AI-generated signals.
  3. Organizer reviews AI flags and supporting evidence.
  4. Organizer approves, rejects, or requests clarification.
- Alternative / Exception Flow:
  - Missing technical metadata leads to clarification request.
  - Suspicious submission may remain under manual review.
- Output:
  - Verification decision and linked AI analysis records.
- Status Transition:
  - Verification: `Pending -> UnderReview -> Verified / Rejected / NeedsClarification`
  - Submission mirrors the final verification outcome.
- Data Affected:
  - Verification Case, AI Analysis Result, Submission, Audit Log
- Related BR:
  - BR-O-006, BR-O-007, BR-P-010, BR-P-011

### F06. Judge Assignment and Evaluation

- Trigger: Organizer opens a judging round for verified submissions.
- Preconditions:
  - Contest and round are active.
  - Submissions are verified.
- Main Flow:
  1. Organizer assigns judges to a round.
  2. Judge opens assigned queue.
  3. Judge scores by criteria and adds comments.
  4. Judge submits evaluation.
  5. System stores criterion scores and total score.
- Alternative / Exception Flow:
  - Judge cannot evaluate a submission twice in the same round.
  - Evaluation outside round deadline is blocked.
- Output:
  - Persisted evaluations and score breakdowns.
- Status Transition:
  - Judge Assignment: `Assigned -> InProgress -> Submitted / Cancelled`
  - Evaluation: `Draft -> Submitted -> Locked`
- Data Affected:
  - Judge Assignment, Evaluation, Evaluation Score, Audit Log
- Related BR:
  - BR-O-008, BR-O-009, BR-P-012, BR-P-013

### F07. Ranking and Result Finalization

- Trigger: Organizer finalizes results after all required judging is complete.
- Preconditions:
  - Required evaluations are submitted for the final round.
- Main Flow:
  1. System aggregates final round scores.
  2. Organizer reviews ranking and tie-breaking evidence.
  3. Organizer finalizes category results.
  4. Organizer assigns awards.
  5. Organizer publishes results.
- Alternative / Exception Flow:
  - Missing evaluations block finalization.
  - Ties require explicit organizer decision or rule-based tie-break.
- Output:
  - Final results, award assignments, publication state.
- Status Transition:
  - Result: `Draft -> Finalized -> Published`
- Data Affected:
  - Result, Award Assignment, Audit Log
- Related BR:
  - BR-O-010, BR-P-014, BR-P-015, BR-P-016

### F08. Digital Archive

- Trigger: Organizer archives winning or selected works after publication.
- Preconditions:
  - Result is finalized.
- Main Flow:
  1. Organizer selects eligible result(s) for archival.
  2. System snapshots key contest, participant, technical, and judging metadata.
  3. Archive item becomes searchable for future reuse.
- Alternative / Exception Flow:
  - Archive creation is blocked before result finalization.
  - Archived snapshot remains immutable even if upstream configuration later changes.
- Output:
  - Stable archive item snapshot.
- Status Transition:
  - Archive Item: `PendingArchive -> Archived -> Retired`
- Data Affected:
  - Archive Item, Audit Log
- Related BR:
  - BR-O-011, BR-P-017, BR-P-018

## 13. Requirement Quality Review

The requirement baseline is considered acceptable for the next phase because:

- Each major business flow is modeled end-to-end.
- Functional requirements are atomic and testable.
- Non-functional requirements constrain the architecture and physical design.
- Business rules are explicitly marked as official or proposed.
- Use cases align directly to the core flows.
- Requirements can be traced to modules, entities, and tests in later phases.
